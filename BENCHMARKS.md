# Benchmarks

Local measurements for the v0.20 performance work (G15). These
numbers were produced on the dev sandbox that built the release —
Python 3.12.3, Linux x86_64, 2 vCPUs — whose wall clock is noisy:
idle shell round-trips on this box take seconds, and absolute
times for the same operation swung ~2x between sessions on
Oct 13, 2026. Treat the PAIRED ratios (same session, same
process pattern, medians of 3) as the reliable figures and the
absolute seconds as indicative only. Nothing here is a claim
about your machine.

Trees: "repo" is GhostSlice itself (95 files, ~352K estimated
original tokens); "synthetic" is a deterministic seeded tree of
2,000 files (60% Python, 20% TS, 10% Markdown, 10% JSON across
40 packages), generated by the same code the test suite uses.

## Pre-optimization profile (where the time went)

cProfile of a synthetic-tree export (~6s in that session):
`tokens.estimate_tokens_raw` ~2.6s cumulative (regex findall +
per-match loop; called at scan and twice per slice), `ast.parse` /
`compile` ~1.5-2.8s for the 1,200 Python files, the TS brace
matcher ~0.7s, file I/O ~0.9s. Conclusion: memoize the pure
derivations (content cache); threading is suspect under the GIL.

## Paired results (Oct 13, 2026, medians of 3, in-process)

| operation | cold / no cache | warm cache | ratio |
|---|---|---|---|
| repo export | 2.61s | 0.085s | ~30x |
| repo scan | 0.43s | 0.08s | ~5x |
| synthetic export (2,000 files) | 4.38s | 0.65s | ~6.8x |
| synthetic scan | 0.68s | 0.21s | ~3.2x |

An earlier session measured the synthetic export at 3.71s cold
(no cache) vs 0.59s warm (~6.3x) and its scan at 0.66s vs 0.20s
(~3.3x) — same ratios, different absolutes.

## Workers (synthetic export, cold, no cache)

| workers | median |
|---|---|
| 1 | 3.71s |
| 2 | 3.53s |
| 4 | 4.00s |

Warm runs were slower with threads (0.78s at the threaded
default vs 0.59s sequential). Verdict: `--workers` defaults to
1; the option is deterministic (byte-identical output at any
count, test-pinned) but is not the win. The cache is.

## Incrementality

Change one file in the 2,000-file tree and re-export: 3,998
cache hits, 2 misses, 2 stores (that file's scan + slice
entries). Cache size for the synthetic tree: 4,000 entries,
~1.9 MB.

## CPU-time pairing (why the test suite times CPU, not wall)

Measured under load on Oct 13, 2026: synthetic cold export
(cache off) 2.26s process CPU vs warm 0.45s CPU (~5x), while
the same runs' WALL times swung from 2.9s to 6.7s cold and
0.43s to 2.3s warm depending on other tenants' I/O. The cache
saves CPU work (tokenize/parse); the suite's >=3x assertion
therefore uses process CPU with the threshold kept at 3x.
A cold fill (cache on, empty cache) costs ~+0.9s CPU over the
cache-off run for the tree's 4,000 stores — the one-time price
of every later warm run.
